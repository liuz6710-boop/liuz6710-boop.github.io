RoleScout

A job search is a filtering problem. So I built the filter: a Python pipeline that pulls postings from ten sources, ranks them against my own résumé, scores fit with an LLM — and measures whether the ranking is actually any good.

— THE PROBLEM

Keyword filters throw away the jobs you actually want.

The first version worked the way most job tools do: a keyword gate on the title. "Product Manager" in, everything else out. It was fast, and it was wrong — it dropped solution roles, forward-deployed roles and analyst roles that fit my experience better than half the PM postings it let through. A title is a label, not a description of the work.

The deeper problem: relevance isn't a binary. It's a ranking, and the only thing that knows what "relevant" means for me is my own résumé.

— THE REDESIGN

Résumé-driven ranking, not keyword gates.

I rewrote the matching pipeline around a single decision: the hard filter only removes what I could never take — not based in Singapore, not full-time — and everything else gets ranked instead of rejected. Rejected postings keep their reason in the database rather than being deleted, so I can re-tune a rule and re-score the backlog without re-fetching a thing.

Ingest

Ten sources — Greenhouse, Lever, Ashby, Workday, SmartRecruiters, MyCareersFuture and more — behind one adapter interface. Idempotent, dedupe-keyed loads, so re-running never duplicates a row.

Rank

Local sentence-transformer embeddings score every posting against the résumé. Free, offline, and it sorts the whole pool instead of cutting it.

Score

An LLM grades fit against a rubric, grounded in the résumé, a structured target profile, and past postings I rated myself — few-shot anchors that pull the model toward my judgement, not a generic one.

Review

A local FastAPI dashboard to read the ranked list and rate results. Those ratings feed straight back into the next run's prompt context.

— MEASURING IT

If you can't evaluate it, you're just guessing.

The hard part of an LLM feature isn't calling the API — it's knowing whether a change made the output better or worse. So the ranking has a scoreboard: a fixture set with known-good answers, precision@k and NDCG@k computed in plain Python, and a threshold gate that fails the run — non-zero exit code — when quality drops below the bar.

  • Evaluation harness — precision@k / NDCG@k over a labelled fixture set, wired into the dev loop as a gate rather than a report nobody reads.
  • Bias regression — the first rubric quietly favoured one role family (product). I rewrote it to score against the target profile instead of a title, and added tests that fail if that bias creeps back.
  • Human-in-the-loop — my own 1–5 ratings are distilled into a short "likes / avoids" summary and injected as calibration examples.
  • Cache invalidation — the target profile is keyed by a hash of the résumé; change the résumé and every stale score is invalidated automatically rather than silently reused.

— MAKING IT RUN UNATTENDED

Everything that talks to a network eventually fails.

A pipeline that only works when you're watching it isn't a pipeline. Most of the engineering effort went into the failure paths — the parts nobody demos.

Retries & backoff

429 and 5xx responses retry with exponential backoff instead of dropping the run. Auth-header handling normalised across two different key formats after a debugging session I did not enjoy.

Graceful degradation

When the model is unreachable, the run still completes: ingestion and embedding ranking carry on, LLM scores are simply marked missing and picked up next time.

Run health

Every run emits a report with OK / WARN / FAIL severity, per-source row counts, per-endpoint HTTP status and the LLM error rate — which is how I found four ATS endpoints quietly returning 404 after a company changed hosts.

Cost control

A top-K cap bounds spend on abnormally high-volume days, so an unusual morning can't turn into an unusual bill.

— WHAT I TOOK FROM IT

Lessons that transfer.

  • Design decisions beat model choices. Replacing the keyword gate with résumé-driven ranking changed the output more than any prompt tweak did.
  • Evaluation is the product. The scoreboard is what makes iteration possible; without it every change is an opinion.
  • Log the reason, not just the verdict. Keeping rejected rows with their reason meant re-tuning rules cost nothing — the same instinct behind keeping audit trails in the systems I build at work.
  • Built with AI, reviewed by me. Written in an AI-assisted workflow (Claude Code) on a ticket → test → eval loop; the tests and the eval gate are what make that trustworthy rather than fast-and-loose.
